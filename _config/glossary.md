# Glossary

| Term | Definition |
|------|-----------|
| **JD** | Job Description. The text of a job listing, downloaded and saved as `job-description.md`. |
| **Grade** | A numeric score (0-10) rating how well a JD matches skills, or how well a resume matches a JD. Stored as a prefix on the filename: `[8] job-description.md`. |
| **JD grade** | Score for how well a JD matches your background (experience, skills, education — everything). Graded against the base resume (primary), informed by the full LinkedIn experience to catch experience not on the generic resume. < 6 → trash. 6–7.9 → rejected. 8+ → proceed. |
| **Resume grade** | Score for how well a customized resume matches a JD. Must be ≥ 9 to proceed. |
| **Passing** | A resume that has grade ≥ 9 AND has passed the truthfulness review. Ready to move to `stages/4_ready/`. |
| **Optimization loop** | Steps 8-10: customize (starting from base resume, sourcing from full experience) → grade → can we improve truthfully? Repeat until no further truthful improvement is possible, regardless of whether the grade is already ≥ 9. The threshold gate (step 11) is a separate check after the loop exits. |
| **Truthfulness review** | Step 12: verify every claim in the resume against the full LinkedIn experience (the superset). No exaggerations or fabrications. Anything not verifiable in LinkedIn → fix or remove. |
| **Base resume** | `_config/profile/base-resume/base-resume.md` — the generic resume. The only customization base: every tailored resume starts from this template. Also the primary JD grading reference. |
| **Full experience** | `_config/profile/full-experience/full-experience.md` — the full LinkedIn career history. Reference pool material for optimal JD match: informs the JD grade (catches experience not on the generic resume) and supplies material the customizer can pull onto the base resume. Never used as a customization base. The truthfulness review verifies against this (the superset). |
| **Auto-reject** | A job moved to `stages/7_trash/<company-role>/` without grading or applying. Two triggers: JD grade < 6, or clearance-required. Periodically deleted by the user. |
| **Clearance-required** | A JD that requires security clearance (active clearance, clearance-eligible, TS/SCI, secret, ability to obtain, etc.). Auto-rejected to `stages/7_trash/`. Detected by the LLM during JD grading (ADR-0007 — no regex filter). The JD grader returns `CLEARANCE` instead of a grade. |
| **Abandon** | Drop a listing without applying. Two reasons: weak fit (JD grade 6–7.9) or couldn't optimize (resume grade < 9). Moved to `stages/6_rejected/` with a reason prefix. |
| **Rejected** | `stages/6_rejected/` — folder for abandoned listings. Subfolders prefixed with `[JOB-FIT]` (weak fit, JD 6–7.9) or `[RESUME]` (couldn't optimize enough). Kept for reference. |
| **Trash** | `stages/7_trash/` — folder for auto-rejected listings (JD grade < 6, or clearance-required). Skimmable but periodically emptied. |
| **Scraper** | The adjacent `job-scraper/` repo. Runs hourly on GitHub Actions, commits results to `output/all_jobs.json`. |
| **`all_jobs.json`** | Rolling master of every scraped job, deduped by URL, stamped with `first_seen`. The source of new jobs for this workspace. **Read-only** from job-hunter's perspective — enrichments go to the sidecar. Currently ~2,432 jobs (7-day rolling window, LinkedIn only). |
| **New job** | A job from the scraper whose URL does not already appear in any stage folder. |
| **Feasibility check** | LLM-based tagging (job-hunter's `pipeline/infrastructure/feasibility_checker.py`, using the configured LLM via `devin_cli.py`) that marks each job with a tripartite verdict: `feasibility: "preferred"` (Big Tech / top-tier fit), `"yes"` (fits but not Big Tech), or `"no"` (doesn't fit). Also sets `feasible: true/false` (true for preferred/yes, false for no). Verdicts stored in the enrichment sidecar (`data/jobs.db`). Prompt in `config.json` → `feasibility_prompt`. Must be run before processing — most jobs are untagged after a backfill. Step 1 of the workflow. |
| **Enrichment sidecar** | SQLite database at `data/jobs.db` that stores pipeline-produced enrichments (feasibility tags + JD descriptions) separate from the scraper's `all_jobs.json`. Replaces the old architecture where the pipeline wrote enrichments directly to `all_jobs.json` (which got lost on every scraper update). Gitignored — regenerable from scraper data + LLM/HTTP fetches. |
| **Prep (Steps 1-2)** | The first two workflow steps, run before any job processing: (1) feasibility check to tag jobs, (2) `fetch_jds` to populate JD descriptions. No folder output — enrichments stored in the sidecar (`data/jobs.db`). `all_jobs.json` is not modified. |
| **Backfill** | Partitioned historical scrape that bypasses LinkedIn's 1000-result-per-query cap using time-sliced location partitions. Saves title/company/location/URL only — no JD text. |
| **`fetch_jds`** | `pipeline/helpers/fetch_jds.py` — fetches JD descriptions from LinkedIn for feasible jobs without descriptions. Reads `all_jobs.json` read-only, writes descriptions to the enrichment sidecar. Has built-in exponential backoff for 429 rate-limiting (30s × 2^attempt, up to 4 retries). |
| **Exponential backoff** | The scraper's `fetch()` function retries 429 responses with wait = 30s × 2^attempt + jitter. `fetch_jds` inherits this. No manual rate-limit handling needed. |
| **`<company-role>`** | The folder naming convention for a single application. E.g. `google-director-of-engineering/`. |
| **DO NOT SUBMIT** | (Deferred) When application form-filling is implemented, the agent fills out the form but stops at the last page. The user reviews and submits manually. |
| **Orchestrator** | `pipeline/__main__.py` + `pipeline/` package — the LangGraph-based control plane that owns pipeline state, per-job graph execution, LLM invocation, and git sync. The primary automation interface. Run via `python3 -m pipeline`. |
| **LLM wrapper** | `pipeline/infrastructure/devin_cli.py` — wraps `devin -p` subprocess calls with model selection, timeouts, and safe error handling. |
| **Clearance detection** | LLM-only (ADR-0007) — the JD grader returns `CLEARANCE` instead of a grade if the job requires security clearance. No regex filter. The old `clearance_filter.py` has been deleted. |
| **Notify** | `pipeline/infrastructure/notify.py` — Pushover notification adapter. No-ops if credentials are missing. Sends run summaries and high-priority alerts for ready/error outcomes. |
| **`.grading/`** | Transient directory for resume grader output. Structure: `.grading/<slug>/grade-vN.json`. Cleaned after processing, gitignored. |
| **`.veracity/`** | Transient directory for truthfulness checker output. Structure: `.veracity/<slug>/verification.json`. Cleaned after processing, gitignored. |
| **`.grades.log`** | Append-only audit trail of every grade (JD and resume). Tracked and committed. |
| **Pipeline state** | `.devin/pipeline-state.json` — persistent state including last scraper SHA and processed URLs. Gitignored. |
| **Pipeline config** | `config.json` — configurable thresholds, timeouts, model names, and iteration caps. Tracked and committed. |
| **the grader model** | Model used for resume grading and truthfulness verification. Separate from the customization model (the customizer model). Used for independent, context-isolated evaluation. |
| **Grading protocol** | `_config/grading-protocol.md` — rubric read by the resume grader. Defines the 0-10 scale, tiered requirement scoring (core vs preferred), score ceiling by gap pattern, bounded subjective synthesis, and JSON output format. |
| **Veracity protocol** | `_config/veracity-protocol.md` — protocol read by the truthfulness checker. Defines how claims are verified against the LinkedIn experience. |
| **Score tampering** | Attempting to change a graded resume's score prefix or overwrite a graded resume. Blocked by the `PreToolUse` hook in `.devin/hooks.v1.json`. |
| **Systemd timer** | `job-hunter-pipeline.timer` — hourly systemd user timer that triggers the pipeline service. Boot catch-up via `Persistent=true`. |
| **Line budget** | The rendered-line constraint on customized resumes: target 70, hard ceiling 75. The few-shot examples range from 69–75 rendered lines. Enforced by the customizer self-measuring with `count_lines` and self-trimming. See ADR-0003. |
| **`count_lines`** | `pipeline/helpers/count_lines.py` — measures rendered line count of a resume markdown file. Run by the customizer during its own turn to self-measure against the line budget. Outputs per-bullet char/line counts + widow flags (diagnostic only — no auto-fix, see ADR-0004). Supports `--json` and `--wrap-chars` (default 102). |
| **Customizer** | The LLM agent that customizes resumes for specific JDs. Pinned to `customizer-model` (`util/agent-profiles/customizer.md`). Draws from the reference pool (base resume, LinkedIn experience, few-shot examples). Self-measures with `count_lines` and self-trims if over the ceiling. The optimizer is the same agent re-invoked with grader feedback. |
| **Reference pool** | The three documents the customizer draws from to optimally match a JD: the base resume (the customization base), the full LinkedIn experience (sourcing material), and the few-shot examples (transformation patterns). Every claim must be truthful — appear in the base resume or LinkedIn. |
| **Exec whitelist** | The `restrict_exec.py` PreToolUse hook — a universal rule (pipeline mode only, `DEVIN_PIPELINE_MODE=1`) restricting exec calls to a two-tier whitelist. Tier 1: `python3 -m pipeline.helpers.count_lines`, `python3 -m pytest`, `mv`, `echo "..." >> .grades.log`. Tier 2: `git`, `gh`, `ls`, `cd`, `cat`, `head`, `tail`, `wc`, `pwd`, `diff`, `grep`, `find`, `which`, `file`, `echo`, `cp`. Chaining allowed if all sub-commands are whitelisted. Blocks `$()`, backticks, single `>`. In debug mode, allows everything. See ADR-0002. |
| **Self-measurement** | The customizer runs `count_lines` during its own turn (rather than a parent-orchestrated loop) to measure rendered lines and self-trim if over the ceiling. Keeps the customizer's context intact. See ADR-0001. |
